0

Foundation: a real data layer

~1 session

Everything downstream lands in a database, so this comes first. SQLite fits the home-server plan perfectly: one file, no service to run, trivial to back up.

  • Replace data/stops.json with SQLite (Drizzle ORM + better-sqlite3). Migrate the 3 existing stops.
  • Extend the schema: stops gain slug, description, coverPhotoId; new posts table (text, timestamp, media, linked stop); new photos table (Dropbox path, taken-at, GPS, stop, curation status); import staging tables so nothing hits the live site without review.
  • Point the existing API routes and admin pages at the database — behavior unchanged, storage swapped.
1

Dropbox importer: rebuild the timeline

~2 sessions · the automation centerpiece

The photo library becomes the source of truth for where you were and when. Dropbox's API returns photo capture time and GPS in file metadata (include_media_info), so most of the scan needs no downloads at all.

  • Scan the backup folder recursively via files/list_folder, collecting time_taken + GPS per photo. Where Dropbox lacks media info, download just the file header and parse EXIF locally (exifr). Results cached to disk so re-runs are incremental — important for a multi-year library.
  • Cluster photos chronologically: consecutive days of photos within a ~10 km radius become a candidate stop with arrival date, departure date, and centroid coordinates. Gaps and travel-day photos define the legs between stops.
  • Name suggestions via reverse geocoding (Nominatim) — candidates arrive as “Moab, UT · Mar 14–29, 2022 · 212 photos” rather than raw coordinates.
  • Review queue in the admin UI: approve, merge, rename, or reject candidates on a map. Approved candidates become real stops.
  • Routes drawn for you: generate the journey polyline between consecutive stops with OSRM road routing, replacing hand-clicked waypoints (the editor stays for touch-ups).
You'll need to: create a Dropbox app (scoped access, files.metadata.read + files.content.read) and generate a refresh token — I'll walk you through it, ~10 minutes — and tell me the folder path of the photo backup.
2

Facebook importer: the blog arrives

~1–2 sessions

One bulk import turns years of “Raffys on the Road” posts into blog entries, each attached to the stop you were at when you posted it.

  • Parse the export's your_posts_*.json: text, timestamp, and attached photos/videos (copied out of the export archive). Includes the fix for Facebook's notorious broken UTF-8 encoding, so em dashes and emoji survive.
  • Auto-link each post to a stop by comparing its timestamp against stop date ranges; a review screen catches the ambiguous ones (travel days, posts written after leaving).
  • Photo upgrade (nice-to-have): Facebook export images are recompressed — where a post photo's timestamp matches a Dropbox original, swap in the full-quality version.
  • Hand-written entries later: imported posts and future entries share one posts table and one editor, so adding new writing is already solved.
You'll need to: request the export at Facebook → Settings → Download your information — choose JSON format, all time, media quality high, and at least “Posts”. Facebook takes hours to a couple of days to prepare it, so kick this off early — it can run while we build Phases 0–1.
3

Photo curation

~1 session to build, then curation at your pace

The site shows the photos you pick, not the whole library. The importer does the sorting; you do the choosing.

  • Every scanned photo is matched to a stop by date and location; a scoring pass suggests ~8 per stop (GPS-tagged, spread across the stay, deduplicated bursts).
  • Admin curation grid per stop: thumbnails stream straight from Dropbox, one click to keep or skip, drag to reorder, star one as the stop's cover photo.
  • Only kept photos are downloaded — resized into web variants (sharp → WebP) and stored on the server's disk. The full-resolution originals stay in Dropbox.
4

The public site

~2 sessions

With real content in place, the map becomes the front door to the story instead of the whole story.

  • Stop pages (/stops/moab-ut): dates, description, photo gallery, and the posts written there.
  • Map upgrades: pin popups with cover photo + dates + link; journey lines colored by trip year instead of alternating red/blue; the placeholder popup and hardcoded “current location” replaced with a proper trip start/end treatment.
  • Blog & timeline: a chronological post index and a scrollable trip timeline as alternate ways in, for family who'd rather read than pan a map.
  • Design pass: typography, mobile layout, and a visual identity worthy of the trip.
5

Ship it: home server + Cloudflare Tunnel

~1 session

Two containers and a tunnel — then it's live for family and friends.

  • Docker Compose: the Next.js app (standalone build) with volumes for the SQLite file and photo directory, plus a cloudflared container running the tunnel. One docker compose up -d on the server.
  • Lock the admin: a Cloudflare Access policy on /admin and write API routes — email one-time-code login for just your addresses. The public map stays open.
  • Backups: nightly job copies the SQLite database and curated photos… back to Dropbox. The trip archive protects the trip site.
  • Update README.md and CLAUDE.md for the new architecture.
You'll need: Docker on the home server, and a domain (or subdomain) on Cloudflare for the tunnel.

Sequencing & what to kick off now

Phases run 0 → 5, but the two imports are independent — the Facebook importer can be built while you're still reviewing Dropbox stop candidates. The only long pole outside our control is Facebook preparing the export, so request it today; the Dropbox app creation is the other 10-minute human task, needed before Phase 1 can run.

RiskReality check & fallback
Photos missing GPSPhone photos are almost always tagged; dedicated-camera photos often aren't. Untagged photos still carry timestamps, so they inherit the stop whose date range contains them — only the stop discovery leans on GPS, and phone photos alone are plenty for that.
Export format quirksFacebook's JSON layout shifts between export versions. The parser is built against your actual export, not documentation, so this is absorbed in Phase 2 rather than discovered late.
Library sizeTens of thousands of photos are fine: the scan is metadata-only, cached, and resumable. Full downloads happen only for the few hundred curated photos.
Clustering judgment callsOvernight stops vs. lunch breaks is a threshold decision. Everything lands in a review queue first — the automation proposes, you approve. Nothing publishes itself.
